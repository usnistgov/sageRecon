# MS2 analyzer -> pass-1 fragment tolerance

**What this is.** The complete set of mass analyzer terms an mzML may legally
carry, taken from the HUPO-PSI controlled vocabulary itself, and the pass-1 MS2
`fragment_tol` recon assigns to each. Written for the methods section: every term
is derivable from a pinned spec snapshot, and every tolerance states whether it
was measured or assumed.

---

## 1. Provenance of the vocabulary

The set of analyzers is defined by the **PSI-MS controlled vocabulary**, not by
any converter and not by any library's copy of it. Converters are written against
this spec, so deriving from it is what makes the table converter-independent.

| field | value |
|---|---|
| source | HUPO-PSI `psi-ms-CV`, file `psi-ms.obo` |
| upstream | `https://raw.githubusercontent.com/HUPO-PSI/psi-ms-CV/master/psi-ms.obo` |
| `data-version` | **4.1.259** |
| released | 23 June 2026 |
| sha256 | `4a615f3bf11685c7225b83bf0e182fc7591065dc5c241c22e5777fb3ccc7b532` |
| pinned copy | `reference-notes/psi-ms-CV/psi-ms.obo` |
| derivation | `testing/scripts/psi_ms_analyzer_terms.py` |
| root term | `MS:1000443` *mass analyzer type* |

**Method.** The script parses every `[Term]` stanza, builds the `is_a` graph, and
walks `MS:1000443` transitively. It yields **12 live descendants and 0 obsolete
terms**. Obsolete terms are reported and excluded.

**To re-derive:**

```
python3 testing/scripts/psi_ms_analyzer_terms.py            # verify + print
python3 testing/scripts/psi_ms_analyzer_terms.py --markdown # regenerate tables
```

The script hard-stops if the snapshot's `data-version` or sha256 drifts from the
pin, if the CV gains an analyzer recon does not classify, if recon names an
accession absent from the CV, or if a term is renamed upstream. It runs as
**Tier 4 of `testing/scripts/run_validation.py`**, so the coverage claim is
checked routinely rather than asserted once.

⚠ Re-running against a newer CV is a **change-regenerate** under AGENTS.md: it
needs an explicit request and a downstream-impact trace. Fetching `master` will
drift; the sha256 pin is what catches it.

## 3. The tolerance, and where each number comes from

**These are deliberately LOOSE pass-1 windows, not performance figures.** Pass 1
must assume the instrument could be well out of calibration, so each window sits
far above typical performance rather than at it. A window that is too wide costs
some specificity; one that is too tight costs the entire search.

| bucket | pass-1 tolerance | typical real-world MS2 error, and rationale |
|---|---|---|
| Orbitrap | +/-20.0 ppm | CURATED. Typical 1-5 ppm, up to ~20 ppm poorly calibrated; the window sits AT that worst case. ⚠ CORRECTED 2026-09-04, was 50.0. |
| AstralTof | +/-20.0 ppm | CURATED. <5 ppm RMS drift over 24h external cal, ~3 ppm internal. Same bucket as Orbitrap: Astral is high-res, not a legacy QTOF. ⚠ CORRECTED 2026-09-04, was 50.0. |
| LegacyTof | +/-100.0 ppm | CURATED. Typical ~10-30 ppm; 30 ppm is already a common default, so the pass-1 window is set well above it. |
| IonTrap | +/-1.0 Da | CURATED. 0.3-0.8 Da typical at unit resolution. A ppm figure is meaningless here. |
| Unclassified | fallback +/-20.0 ppm | FALLBACK. No bucket. recon does not halt: it searches at the fallback window and reports that it assumed. |

### Provenance, and what is NOT curated

The curated source (`reference-notes/analyzer-tolerances/`) names **6 of the 12**
CV analyzer terms. The other 6 are assigned here by CV parentage and are marked
`extended here` in the table above:

| term | assigned to | why |
|---|---|---|
| `MS:1000079` FT-ICR | Orbitrap bucket | High-resolution FT, same accuracy regime as the Orbitrap. |
| `MS:1000264` ion trap | IonTrap bucket | **The generic parent, and the only ion-trap term ThermoRawFileParser writes.** Omitting it would miss every Thermo-converted ion-trap file. |
| `MS:1000291` linear ion trap | IonTrap bucket | Parent of the two curated linear-trap children. |
| `MS:1000081` quadrupole | IonTrap bucket | Unit resolution; the curated bucket is named "low-res, quad-like". |
| `MS:1000080` magnetic sector | no bucket | Not a proteomics MS2 analyzer; falls back and reports. |
| `MS:1000254` electrostatic energy analyzer | no bucket | As above. |

⚠ **The curated figures carry unresolved citation fragments** (e.g.
`pmc.ncbi.nlm.nih+1`, `support.proteinmetrics`, `pure.mpg+1`). These are
placeholders, not references. **They must be resolved to real citations before
publication.** The numbers are endorsed by the project owner and are used as-is;
the sourcing is the open item.

### The one bucket measured in this repo

The Orbitrap window is the only one any local data touches. MSFragger's
pre-calibration ("Old") MS2 median and MAD over the three reference files, from
`testing/reference-data/msfragger/{strictTryp,semiTryp}/log_*.txt`:

| file | MS2 median (ppm) | MAD (ppm) | abs(median) + 3*MAD |
|---|---|---|---|
| serum, run 001 | +0.96 | 1.33 | 4.95 |
| bcell, run 002 | +0.96 | 2.49 | **8.43** |
| b1906, run 003 | -0.05 | 1.62 | 4.91 |

The +/-20 ppm window contains the worst case with 2.4x headroom (20 / 8.43). The
invariant is asserted in `recon-tool/tests/analyzer_detection_integration.rs`
(`orbitrap_tolerance_contains_the_measured_ms2_error`).

⚠ **CORRECTED 2026-09-04. This read "+/-50 ppm ... 5.9x headroom".** The window
was tightened from 50 to 20 on 2026-08-31. The headroom is smaller and that is
the point: 50 ppm was wider than the unknown-analyzer fallback, so a correctly
detected Orbitrap searched worse than an undetectable file.

**No local data exercises the Astral, legacy-TOF or ion-trap buckets.** All three
reference files are Orbitrap MS2, confirmed independently by MSFragger reading
the RAW. Per AGENTS.md a synthetic fixture cannot settle those numbers.

## 4. How recon reads the analyzer

Two signals exist, and they are not equally good. Recon prefers the **per-scan
Thermo filter string** (`MS:1000512`) and falls back to the file-level
`instrumentConfiguration` analyzer term.

1. **Filter string, preferred.** Its first token is the analyzer that acquired
   *that scan*: `FTMS`, `ITMS`, `TOFMS`, `ASTMS`, `TQMS`, `SQMS`, `Sector`.
   Being per-scan, it can express "FT MS1, ion-trap MS2" inside one run, which
   the file-level term cannot. Present on 100% of 229,348 spectra across the
   three reference files.
2. **`instrumentConfiguration` CV term, fallback.** Correct for non-Thermo data,
   which carries no filter string. Honoured per-scan through
   `instrumentConfigurationRef`, so a multi-configuration hybrid from msconvert
   is read correctly.

**Why the filter string wins, concretely.** `B.naive_01steady-state.mzML.gz` is a
**Q Exactive Plus** but declares `MS:1000079` FT-ICR — an instrument with no ICR
cell. ThermoRawFileParser mapped every Orbitrap to FTICR until 1.4.4, whose
release notes read *"Using CVTerm 'Orbitap' instead of 'FTICR' for Orbitrap-based
instruments (closes #177)"* (2024-05-10). That file was converted with 1.4.2. The
filter string is immune: Orbitrap and FT-ICR both report `FTMS` and both are
high-resolution, so the tolerance is unchanged. Asserted by
`the_thermo_fticr_mislabel_cannot_change_the_tolerance`.

**A trap worth recording.** ThermoRawFileParser maps its `MassAnalyzerITMS` to
the *generic parent* `MS:1000264` "ion trap", not to any specific child. A table
listing only `MS:1000082`/`MS:1000291` would miss every Thermo-converted
ion-trap file — the exact case this feature exists to catch. All five ion-trap
terms are classified.

### Sampling

Detection reads the first **100 MS2 scans** and stops; MS1 fills opportunistically
alongside. An acquisition method does not swap the MS2 detector mid-run, so the
head of the run answers the question. It uses a streaming, non-indexed,
metadata-only reader, so a gzipped input is decompressed only as far as the
sample: **0.04-0.42 s per file** on inputs of 164-448 MB.

The stopping rule waits for the MS2 sample however deep it lies. This is not
theoretical: in `2019-4-9_909c_0311` the first MS2 is at spectrum 140 and **2063
MS1 scans precede the 100th MS2**. A naive "first N spectra" cap would have
sampled almost no MS2 on that file.

### recon never refuses to search

Analyzer detection can never be the reason a search does not run. Every path
yields a tolerance; the ones recon had to assume are flagged and reported.

| situation | what recon does |
|---|---|
| One analyzer detected, with a bucket | Uses that bucket. `basis = Detected`. |
| Analyzer detected, no bucket (sector, electrostatic) | Falls back to +/-20 ppm, `assumed = true`, reports. |
| No analyzer readable at all | Falls back to +/-20 ppm, `assumed = true`, reports. |
| **MS2 detector CHANGES inside the run** | Falls back to +/-20 ppm, `assumed = true`, and **names both detectors** in the report. |

A run that switches MS2 detector has no single correct pass-1 tolerance, because
one search runs at one `fragment_tol`. recon states what it saw and what it
assumed rather than halting or silently picking a winner.

**The fallback is +/-20 ppm, which now EQUALS the Orbitrap bucket it usually
stands in for.** +/-20 ppm is the value every pass-1 template already hardcodes,
so an undetectable file gets recon's existing behaviour. It is reported every
time it is used.

⚠ **CORRECTED 2026-09-04. This read "TIGHTER than the +/-50 ppm Orbitrap
bucket".** That stopped being true on 2026-08-31, when the Orbitrap bucket moved
to 20. The two are now the same number, so failing to detect an Orbitrap costs
nothing on the tolerance. See `mzml.rs`, which records the same correction.

### The template's `fragment_tol` is overridden, not trusted

Every pass-1 template in this repo hardcodes `fragment_tol: {ppm: [-20, 20]}`
regardless of instrument. `run` therefore **replaces** it with the detected
bucket's value before Sage starts, and writes the result to
`<search-dir>/effective-params.json`. That artifact carries a
`_recon_fragment_tol_provenance` block recording the template's original value,
the value applied, the basis, and the analyzers seen at both MS levels — so what
was actually searched is recoverable rather than implicit.

This has to happen before the search. The tolerance is a pass-1 INPUT: a search
run at a ppm window against ion-trap MS2 matches almost nothing, and no
downstream step can recover PSMs that were never made.

## 5. Known limitations

1. **Only the FT branch is validated on real data.** All three reference files
   are FTMS at both MS levels, confirmed independently by MSFragger reading the
   RAW (`MS2 ITMS = false; MS2 FTMS = true`). The ion-trap, TOF and quadrupole
   numbers are assumptions. Per AGENTS.md a synthetic fixture cannot settle them;
   a real ion-trap file is required.
2. **Head sampling cannot see a mid-run switch.** Detection samples the start of
   the run, so a file that changes MS2 analyzer part-way is not caught unless the
   sample straddles the boundary. Recorded rather than papered over.
3. **The ppm ladder `{10,20,50,100}` serves MS1 AND a ppm-class MS2.** It is
   never applied to a Da-class MS2. Asserted by
   `the_ms1_ppm_ladder_never_reaches_a_low_res_ms2`, whose name says the real
   rule: not "never MS2", but never a LOW-RES MS2.

   ⚠ **CORRECTED 2026-09-04. This read "is MS1-only and is never applied to
   MS2".** That was wrong from 2026-09-03, when the report moved to one combined
   `Recommended MS1 / MS2`. `calibration.rs::ms2_user_recommendation` quantizes a
   ppm analyzer onto this same ladder (`FragmentTolerance::Ppm(ladder_rung(..))`)
   and sends a Da analyzer down the m/z 500 conversion instead. The protection
   the old wording was reaching for still holds: a ladder rung is meaningless for
   an ion trap, and any Da analyzer in a mixed census wins.
