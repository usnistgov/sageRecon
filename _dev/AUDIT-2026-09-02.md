## ⛔ 1. Windows absolute paths are broken by the Sage v0.15 upgrade

`sage-cloudpath` now calls `Url::parse(s)` FIRST and returns early on success
(`sage-cloudpath/src/lib.rs:19-26`). Measured with url 2.5.8, the version in our
`Cargo.lock:3596`:

```
Url::parse("C:\\data\\raw\\b1906.mzML.gz")  ->  OK  scheme="c"  path="\\data\\raw\\b1906.mzML.gz"
```

A drive letter parses as a URL SCHEME, so `from_file_path` is never reached.
v0.14.7 used `http::Uri` and fell through to a local path.

`sage_runner.rs:143` and `:147-153` pass the user's raw `<MZML>` and `--fasta`
strings straight through. `output_directory` has the same shape.

**Effect:** `recon run C:\data\b1906.mzML C:\db\human.fasta --enzyme trypsin`
fails on the shipped `windows-64` build where v0.14.7 worked.

⚠ **UNVERIFIED end to end** — no Windows machine available. The `Url::parse`
behaviour is measured and platform independent; the end-to-end failure is
inferred from it. **Verify on Windows before fixing.**

**Status: FIXED, `8a27b3e`.** recon now builds the `file://` URL itself before
handing it to Sage, so Sage gets what it would have built under v0.14.7. A
real URL (scheme longer than one character) still passes through untouched.
Still unverified end to end on an actual Windows machine — the commit message
repeats the same caveat.

## ⛔ 2. Any mzML with a space or non-ASCII character in its name now hard-aborts

v0.15 derives `filename` from `Url::path()`, so it is PERCENT-ENCODED
(`sage-cloudpath/src/lib.rs:36-38`). v0.14.7 returned the name verbatim.
Measured:

```
"/path/to/my file #1.mzML.gz"  ->  filename = "my%20file%20%231.mzML.gz"
"/path/to/Grüße.mzML"          ->  filename = "Gr%C3%BC%C3%9Fe.mzML"
```

`main.rs:1608-1611` builds the basename with `Path::file_name()` and
`main.rs:1623` demands EXACT string equality against the TSV's `filename`.

**Effect:** `recon analyze` aborts with "provenance guard (open TSV): --mzml
basename ... is not present". Our three test files are plain ASCII, so nothing
caught it. A space in a filename is not an edge case.

**Status: FIXED, `8a27b3e`.** `distinct_filenames` now percent-decodes before
the provenance-guard comparison. Regression test writes a real TSV and checks
a space, a `#`, and a non-ASCII character.

## ⚠ 3. `mass_accuracy.precursor_*_ppm` changed meaning with no schema note

`precursor_ppm` became SIGNED in v0.15. Measured: 17591 of 68817 rows negative,
min -121568.77. `fragment_ppm` stayed absolute (0 of 68817 negative).

The docs still say otherwise. `report.rs:370-372` — "ALL FOUR ppm fields below
are medians of |error| ... **None of them can be negative**". `report.rs:384`
— "Precursor (MS1) median **ABSOLUTE** ppm". `report.rs:62-65` — "The four
`mass_accuracy.*_ppm` fields are NOT affected".

**The committed data already contradicts them:** `full-run/liver.json` has
`precursor_median_ppm: -0.2771486`. A negative value in a field whose own doc
says it cannot be negative. The schema version-history block stops at 1.7.0
while `SCHEMA_VERSION` is 2.1.0, and no entry records this change of MEANING.

Related: `precursor_p95_ppm` was a coverage bound under v0.14 ("95% of PSMs
within X ppm"). It is now the 95th quantile of a signed distribution. No code
change, but the label is wrong.

**Status: FIXED IN PART, `8a27b3e`.** `sage_results.rs` and `qc.rs` were
corrected. `qc.rs:55-60` now documents `precursor_ppm` as SIGNED, with the
measurement (17591 of 68817 rows negative, min -121568.77) written into the
comment.

⚠ **STILL OPEN: `report.rs` was not corrected and now contradicts `qc.rs`.**
`report.rs:370-395`, the doc for the `MassAccuracySummaryReport` struct that
`precursor_median_ppm` actually comes from, still reads "ALL FOUR ppm fields
below are medians of |error| ... which the pinned Sage reports as absolute
values. None of them can be negative" and "Precursor (MS1) median ABSOLUTE
ppm." Two files apart, one doc says signed and the other says it cannot be
negative. The committed `testing/recon-output/full-run/liver.json:1580` still
reads `"precursor_median_ppm": -0.2771486` — unchanged, still negative, still
contradicting `report.rs`'s own struct doc.

Also still open: the schema version-history block in `report.rs` (the doc
comment above `pub const SCHEMA_VERSION`) still stops its entries at 1.7.0.
`SCHEMA_VERSION` is now 2.1.0, and no 1.8.0/2.0.0/2.1.0 entry records the
v0.15 meaning change to `precursor_ppm`.

## ⚠ 4. The upgrade instruction in `calibration.rs` is WRONG — do not follow it

`calibration.rs:71-73` instructs a future session to "REMOVE the reconstruction
in `from_psm`" when adopting v0.15. **Following it would corrupt the MS1 bias.**

`signed_precursor_ppm` divides by `calcmass`; Sage divides by a MEAN mass
(`crates/sage/src/scoring.rs:532-533`). Measured on serum's clean subset
(n=3770): mean |diff| 0.021 ppm, max 0.092 ppm, **0 sign flips** — agreement.
Across all 68817 rows: mean |diff| **7026 ppm** — the open window makes the
denominators diverge. Deleting the reconstruction imports that error.

The instruction was not followed, which was luck rather than judgement. Correct
the comment so nobody follows it later.

**Status: FIXED, `ddaf5ab`** ("Correct an upgrade instruction that would have
corrupted the MS1 bias"). This commit is not in the `58b74a8..HEAD` range
listed at the top of this file — it landed after that range was checked,
concurrently with this audit update. Verified directly against the current
`calibration.rs:64-85`: the comment now reads "DO NOT REPLACE THIS WITH
SAGE'S COLUMN" and records the measurement — clean subset n=3777, mean |diff|
0.021 ppm, 0 sign flips; all rows n=68817, mean |diff| 7026 ppm, 0 sign flips.
The sibling `fragment_ppm` comment was corrected in the same commit.

## ⚠ 7. The CURATED_MODS bug class has a second instance — in the tier tests

`CuratedDb::load` (the DISK path) is called by four test files and NEVER by
production, which uses `load_from_sources` (`main.rs:1867`). **The tests that
validate tier recommendations exercise a route the shipped binary does not
take.** This is the exact shape that let v0.1.0 ship with no recommendations.

Same pattern: `write_effective_params` / `write_pass2_params` are used only by
tests; production calls the `_from_text` variants. The no-mods guard and the
pass2-wiring gate therefore never see `enzyme::apply_to_params_text`, which
production applies immediately before (`main.rs:2499`, `main.rs:2221`).

**Status: FIXED, `2493973`.** The tier and curated gates now call
`load_from_sources` with `defaults::CURATED_MODS`, the embedded route
`main.rs` takes. The params gates now run the production sequence: read text,
apply the enzyme, write from text. Falsified before being kept — removing the
enzyme step from the test helpers made four test files fail.
